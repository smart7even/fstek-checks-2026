# 11.5. ЗКО.5 Изоляция контейнеров в контейнерных средах

**Скрипт:** `fstek_audit/checks/ZKO/ZKO_05.sh`

Цель: Предотвращение несанкционированного доступа из одного контейнера к ресурсам других контейнеров и хостовой операционной системы.

Регламентирование: Не предъявляются.

Описание реализации, действий и результатов при испытаниях:

| Требование | Действие | Результат |
|------------|----------|-----------|
| В контейнерной среде должна обеспечиваться изоляция областей памяти, относящихся к различным контейнерам. | 1. Запустить два контейнера: `docker run -d --name zko5a --memory 64m alpine sleep 3600` и `docker run -d --name zko5b --memory 64m alpine sleep 3600` (аналогично `podman run`, `crictl run`, два Pod в Kubernetes).<br><br>2. Из контейнера A прочитать `/proc/<pid-B>/mem` и `/dev/mem`; выполнить `kubectl exec zko5a -- cat /proc/1/root` относительно процесса контейнера B.<br><br>3. Сравнить cgroup памяти: `docker inspect --format '{{.HostConfig.Memory}} {{.State.Pid}}'`, `cat /sys/fs/cgroup/memory/docker/*/memory.limit_in_bytes`. | 1. Успех: Контейнеры запущены в раздельных cgroup/пространствах.<br><br>2. Успех: Чтение памяти другого контейнера и хоста невозможно.<br><br>3. Успех: Области памяти разграничены лимитами cgroup. |
| Должна обеспечиваться недоступность записи в корневую файловую систему хостовой операционной системы для программного обеспечения, выполняемого внутри контейнера. | 1. Запустить контейнер без `--privileged` и без bind `/`: `docker run --rm -it alpine sh`, `podman run --read-only`, Pod с `readOnlyRootFilesystem: true`.<br><br>2. Изнутри выполнить `touch /host/etc/passwd`, `mount -o remount,rw /`, запись в bind-mount `/etc` хоста.<br><br>3. Попытаться `kubectl apply` манифеста с `hostPath: path: /` и `privileged: true`. | 1. Успех: Контейнер запущен с read-only rootfs и без privileged.<br><br>2. Успех: Запись в корневую ФС хоста невозможна.<br><br>3. Успех: Admission/PSS отклоняет privileged и hostPath на `/`. |
| Должно обеспечиваться ограничение прав программного обеспечения, выполняемого внутри контейнера, на использование периферийных устройств, устройств хранения данных и съемных машинных носителей информации (блочных устройств), входящих в состав информационной системы. | 1. Запустить контейнер без `--device`.<br><br>2. Изнутри обратиться к `/dev/sda`, `/dev/nvme0n1`, `/dev/bus/usb` (`dd if=/dev/sda of=/tmp/x bs=512 count=1`).<br><br>3. Выполнить `docker run --device /dev/sda` и `kubectl apply` с `volumeDevices` от имени непривилегированного пользователя. | 1. Успех: Устройства хоста в контейнер не проброшены.<br><br>2. Успех: Обращение к блочным устройствам и периферии невозможно.<br><br>3. Успех: Запуск с `--device` / `volumeDevices` отклонён политикой. |
| Должно обеспечиваться ограничение прав программного обеспечения, выполняемого внутри контейнера, на использование вычислительных ресурсов (оперативной памяти, операций ввода-вывода за период времени) хостовой операционной системы. Меры реализуются за счет встроенных механизмов средства контейнеризации и хостовой ОС. | 1. Задать лимиты: `docker run --memory 64m --cpus 0.5 --device-write-bps /dev/sda:10mb`, `podman run --memory`, Pod `resources.limits.memory/cpu` и `ephemeral-storage`.<br><br>2. Внутри контейнера запустить потребление памяти (`dd if=/dev/zero of=/dev/shm`) и интенсивный I/O.<br><br>3. Проверить cgroup: `docker stats`, `kubectl top pod`, OOM/throttling. | 1. Успех: Лимиты памяти, CPU и I/O назначены.<br><br>2. Успех: Нагрузка создана.<br><br>3. Успех: Потребление ограничено лимитами; исчерпание ресурсов хоста не происходит. |
| Условия: У Системы К2, К1.<br><br>Должна обеспечиваться изоляция пространств идентификаторов процессов контейнеров; пространств имен для межпроцессного взаимодействия; пространств имен для пользователей и групп; пространств имен хостов и доменов; сетевых пространств имен; пространств имен для иерархии каталогов контейнеров. | 1. Запустить контейнеры без `pid=host`, `ipc=host`, `uts=host`, `net=host`, `userns=host`: `docker run --name zko5ns alpine sleep 3600`; аналогично Pod без `hostPID/hostIPC/hostNetwork`.<br><br>2. Из контейнера A: `ps aux` (не видны процессы хоста и контейнера B); `ip link` (свой стек); `hostname` (не имя хоста); `lsns`; попытка `kill` PID хоста.<br><br>3. Проверить user namespace: `docker inspect --format '{{.HostConfig.PidMode}} {{.HostConfig.IpcMode}} {{.HostConfig.NetworkMode}} {{.HostConfig.UtsMode}}'`, `userns-remap` / rootless Podman, `crictl inspect`. | 1. Успех: Контейнеры запущены с изолированными namespace (PID, IPC, UTS, net, user, mount).<br><br>2. Успех: Процессы, IPC, hostname, сеть и каталоги хоста/другого контейнера недоступны.<br><br>3. Успех: Режимы host namespace и privileged отсутствуют. |
| Автопроверка Linux-хоста | `./check_all.sh --measure ЗКО.5 --class K3`<br><br>`./check_all.sh --measure ЗКО.5 --class K2 --with-enhancements` | Зафиксированы вердикты PASS/FAIL/SKIP/NA по локальным признакам (read-only rootfs/MAC, seccomp, cgroups, отсутствие privileged и mount `/`, `--device`, изоляция PID/IPC/UTS/net/user/mount). SKIP не считается провалом испытания СПО. |

Требования к усилению:

1) должна обеспечиваться:
изоляция пространств идентификаторов процессов контейнеров;
изоляция пространств имен для межпроцессного взаимодействия контейнеров;
изоляция пространств имен для пользователей и групп контейнеров;
изоляция пространств имен хостов и доменов контейнеров;
изоляция сетевых пространств имен контейнеров;
изоляция пространств имен для иерархии каталогов контейнеров.
