# 21.1. МСЭ.1 Сегментация сети

**Скрипт:** `fstek_audit/checks/MSE/MSE_01.sh`

Цель: Обеспечение изоляции сегментов информационной системы друг от друга.

Регламентирование: В эксплуатационной документации на информационную систему должен быть определен:

- порядок сегментации информационной системы.

Описание реализации, действий и результатов при испытаниях:

| Требование | Действие | Результат |
|------------|----------|-----------|
| В информационной системе должна быть реализована сегментация информационной системы путем выделения сетевых сегментов (например, внутренняя сеть, сеть гостевого доступа), функциональных сегментов, сегментов с различным уровнем значимости информации, сегментов с различными классами защищенности, сегментов с различными типами устройств, сегментов виртуальной и контейнерной среды. | 1. Сверить схему сегментации в эксплуатационной документации с фактическими интерфейсами и VLAN: `ip -br addr`, `ip -d link show`, `bridge vlan show` (при наличии), перечень зон `firewall-cmd --get-active-zones`.<br><br>2. На хосте пользовательского сегмента выполнить `ping -c 3 <шлюз своего VLAN>` и `ping -c 3 <шлюз чужого VLAN без разрешенного потока>`.<br><br>3. Для виртуальной и контейнерной среды проверить отдельные сети: `ip netns list`, `docker network ls` / `kubectl get networkpolicy -A` (если стек присутствует). | 1. Успех: Фактические сегменты (интерфейсы, VLAN, зоны) соответствуют перечню в эксплуатационной документации.<br><br>2. Успех: Связность внутри своего сегмента есть; прямой ICMP в чужой сегмент без разрешенного потока отсутствует.<br><br>3. Успех: Виртуальная и контейнерная среды выделены в отдельные сегменты либо в документации зафиксировано их отсутствие. |
| При сегментации информационной системы должны обеспечиваться контроль и фильтрация сетевого трафика на границах сегментов. | 1. Выгрузить правила границы: `nft list ruleset` или `iptables -S; iptables -t nat -S; iptables -t filter -S FORWARD`.<br><br>2. С хоста сегмента А выполнить `nc -zv <IP сегмента Б> <порт без правила>` и `nc -zv <IP сегмента Б> <разрешенный порт>`.<br><br>3. Повторить попытку с подменой исходящего интерфейса/VLAN, если это предусмотрено стендом. | 1. Успех: На границах сегментов есть явные правила accept/drop (nft/iptables/firewalld), а не политика «разрешить всё».<br><br>2. Успех: Неразрешенный порт блокируется (timeout/refused по политике МЭ); разрешенный поток проходит.<br><br>3. Успех: Обход границы сегмента невозможен. |
| Должен быть обеспечен принцип минимальных привилегий при взаимодействии между сегментами, при предоставлении доступа субъектов доступа в сегменты информационной системы. | 1. Сопоставить матрицу разрешенных потоков из документации с `nft list ruleset` / `iptables -S FORWARD`.<br><br>2. С АРМ пользовательского сегмента выполнить `nc -zv <IP СУБД> 5432` (или иной порт БД по схеме) при отсутствии такого потока в матрице.<br><br>3. С сервера прикладного сегмента выполнить разрешенный поток к СУБД по тому же порту. | 1. Успех: В правилах МЭ нет избыточных any-any между сегментами; каждый межсегментный поток имеет субъекта, порт и направление.<br><br>2. Успех: Прямой доступ АРМ к СУБД блокируется.<br><br>3. Успех: Разрешенный прикладной поток к СУБД проходит. |
| Указанные меры реализуются за счет применения межсетевых экранов, и (или) многофункциональных межсетевых экранов уровня сети, и (или) средств однонаправленной передачи информации, а также (при необходимости) за счет физической изоляции отдельных сегментов, определяемых оператором. | 1. Проверить активность МЭ: `systemctl is-active nftables firewalld ufw netfilter-persistent`; `nft list ruleset \| head`.<br><br>2. При заявленной однонаправленной передаче/физической изоляции сверить наличие data diode / отсутствие обратного маршрута: `ip route get <IP изолированного сегмента>` с обеих сторон. | 1. Успех: Межсетевой экран активен, правила загружены.<br><br>2. Успех: Для физически изолированных или однонаправленных сегментов обратный маршрут отсутствует либо трафик принимается только средством однонаправленной передачи. |
| При сегментации информационной системы должна проводиться проверка корректности сегментации в соответствии с эксплуатационной документацией, но не реже одного раза в год. | 1. В эксплуатационной документации найти регламент и дату последней проверки корректности сегментации.<br><br>2. Выборочно сверить 3–5 потоков из акта проверки с текущими ACL (`nft list ruleset`). | 1. Успех: Порядок и периодичность (не реже одного раза в год) зафиксированы, акт не старше года.<br><br>2. Успех: Зафиксированные потоки совпадают с действующими правилами МЭ. |
| Субъект: Нагрузки внутри сегмента.<br><br>Условия: У Системы К1.<br><br>Должна быть реализована микросегментация на уровне сегментов информационной системы, обеспечивающая их разделение на изолированные сегменты. | 1. Проверить политики внутрисегментной изоляции: `kubectl get networkpolicy -A` / правила Calico/Cilium/OVS; `nft list ruleset` на признаки `iifname`+`oifname`, `ip saddr`+`ip daddr` между нагрузками.<br><br>2. С workload A выполнить `nc -zv <IP workload B> <порт без policy>` и повтор с портом, разрешенным policy. | 1. Успех: Обнаружены политики микросегментации (NetworkPolicy, security groups, поадресные правила nft), а не только периметр VLAN.<br><br>2. Успех: Трафик между нагрузками без policy блокируется; разрешенный поток проходит. |
| Автопроверка Linux-хоста | `./check_all.sh --measure МСЭ.1 --class K3`<br><br>`./check_all.sh --measure МСЭ.1 --class K1 --with-enhancements` | Зафиксированы вердикты PASS/FAIL/SKIP/NA по локальным признакам (несколько интерфейсов/VLAN, активный МЭ, регистрация в правилах, документация сегментации; для К1 — микросегментация). SKIP не считается провалом испытания СПО. |

Требования к усилению:

1) должна быть реализована микросегментация на уровне сегментов информационной системы, обеспечивающая их разделение на изолированные сегменты;
2) должна быть реализована возможность предоставления доступа внешних пользователей к приложениям (сервисам) информационной системы без предоставления доступа к иным сегментам информационной системы;
3) должна быть реализована автоматизация управления правилами фильтрации в сегментах информационной системы для обеспечения согласованности правил на различных межсетевых экранах;
4) должны централизовано регистрироваться события блокировки попыток доступа в обход определяемых оператором правил межсетевого экранирования с применением средств мониторинга информационной безопасности.
