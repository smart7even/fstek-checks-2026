# 23.4. ЗКС.4 Контекстная проверка исходящего трафика

**Скрипт:** `fstek_audit/checks/ZKS/ZKS_04.sh`

Цель: Предотвращение утечки информации ограниченного доступа и выявление несанкционированного обмена данными путем анализа исходящего сетевого трафика.

Регламентирование: Не предъявляются.

Описание реализации, действий и результатов при испытаниях:

| Требование | Действие | Результат |
|------------|----------|-----------|
| В информационной системе должна быть реализована контекстная проверка исходящего сетевого трафика, направляемого за пределы контролируемой зоны, включая сеть «Интернет». | 1. Идентифицировать средство проверки (DLP/ICAP/прокси с инспекцией): службы Solar Dozor / InfoWatch / SearchInform / c-icap, `grep -R icap /etc/squid`, `ssl_bump`.<br><br>2. С внутреннего хоста отправить через контролируемый канал тестовый файл с маркером ограниченного доступа: `curl -x http://<прокси>:3128 -F file=@secret.txt https://<внешний приемник стенда>`. | 1. Успех: Контекстная проверка исходящего трафика за пределы КЗ включена (не только наличие прокси без политики содержимого).<br><br>2. Успех: Передача маркера блокируется или помещается на карантин; событие появляется в журнале DLP/прокси. |
| Проверка должна включать анализ содержания, метаданных и поведенческих характеристик передаваемых данных. | 1. Содержание: повторно передать файл с контрольной строкой/шаблоном (учетные данные, метка грифа) через `curl -x ... -F`.<br><br>2. Метаданные: передать файл с тем же содержимым, но измененным именем/MIME (`Content-Type: application/octet-stream`) и в архиве.<br><br>3. Поведение: серия исходящих сессий на нетипичный внешний хост с сервера, для которого такой обмен не предусмотрен (`curl` в цикле). | 1. Успех: Срабатывание по содержимому.<br><br>2. Успех: Срабатывание сохраняется при смене имени/типа (анализ не только расширения).<br><br>3. Успех: Нетипичный исходящий обмен выявляется как аномалия поведения. |
| Должно обеспечиваться выявление аномальной активности в сетевом трафике. | 1. Снять базовый профиль исходящих соединений узла (`ss -tulpn`, график мониторинга).<br><br>2. Имитировать аномалию: массовый исходящий поток на внешний IP вне whitelist (`nc`/`curl` пакетом запросов) либо передача в нерабочее окно, если оно задано оператором. | 1. Успех: Базовый профиль исходящей активности известен средству контроля.<br><br>2. Успех: Аномалия зафиксирована (блок и/или алерт), продуктивный разрешенный поток не затронут. |
| Должны быть определены и контролироваться сетевые порты, приложения и сервисы, используемые для передачи данных за пределы контролируемой зоны, включая сеть «Интернет». | 1. Сверить перечень исходящих портов/приложений в политике с `nft list ruleset` OUTPUT и ACL прокси (разрешенные 443/прокси-порт, запрет прочих).<br><br>2. `nc -zv <внешний IP> 443` через разрешенный канал и `nc -zv <внешний IP> 22` напрямую. | 1. Успех: Порты, приложения и сервисы исходящей передачи определены и отражены в правилах.<br><br>2. Успех: Разрешенный исходящий канал проходит проверку; неразрешенный порт блокируется. |
| Автопроверка Linux-хоста | `./check_all.sh --measure ЗКС.4 --class K3` | Зафиксированы вердикты PASS/FAIL/SKIP/INFO/NA по локальным признакам (DLP/ICAP/контекстная политика, контроль исходящего доступа). Наличие одного proxy/ssl_bump без политики содержимого недостаточно для PASS. SKIP не считается провалом испытания СПО. |

Требования к усилению:

1) должны применяться системы глубокого анализа пакетов для выявления аномалий в сетевом трафике;
2) должны использоваться механизмы поведенческого анализа активности пользователей;
3) должны использоваться специализированные компоненты (агенты) на конечных устройствах пользователей с целью анализа исходящего трафика;
4) должны реализовываться механизмы выявления и блокировки попыток маскировки данных;
5) должны использоваться системы контроля использования облачных сервисов;
6) должны внедряться механизмы классификации данных на основе анализа содержимого.
