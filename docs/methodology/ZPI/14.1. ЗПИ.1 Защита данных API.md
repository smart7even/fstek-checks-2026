# 14.1. ЗПИ.1 Защита данных API

**Скрипт:** `fstek_audit/checks/ZPI/ZPI_01.sh`

Цель: Исключение несанкционированного доступа к СПО при использовании программных интерфейсов взаимодействия приложений (API).

Регламентирование: В эксплуатационной документации для СПО должны быть определены:

- перечни API, предоставляемых внешним и внутренним пользователям СПО;
- требования к режимам и настройкам программного обеспечения, обеспечивающим конфиденциальность информации и служебных данных, передаваемых при получении доступа и взаимодействии с API.

Описание реализации, действий и результатов при испытаниях:

| Требование | Действие | Результат |
|------------|----------|-----------|
| При организации сетевого взаимодействия между субъектами доступа (пользователями и приложениями) и объектами доступа посредством API должна обеспечиваться минимизация объема информации, раскрывающей структуру информационной системы, или иной информации, передаваемой посредством API. | 1. Выполнить к https://example.ru/api документированные методы от имени внутреннего и внешнего клиента.<br><br>2. Вызвать несуществующий метод и метод без необходимых параметров.<br><br>3. Сравнить состав ответов с перечнем API и требованиями к режимам из эксплуатационной документации. | 1. Успех: Ответы содержат только данные, необходимые для функции метода.<br><br>2. Успех: Ответы не раскрывают внутреннюю структуру СПО (пути, имена узлов, стек, служебные идентификаторы сверх необходимого).<br><br>3. Успех: Состав передаваемых данных соответствует документации. |
| В СПО должна обеспечиваться минимизация состава информации, возвращаемой в сообщениях об ошибках взаимодействия с API, раскрывающей структуру и особенности функционирования информационной системы или иную конфиденциальную информацию. | 1. Отправить на https://example.ru/api запрос с неверным синтаксисом, неверным типом поля и обращением к отсутствующему ресурсу.<br><br>2. Отправить запрос, вызывающий прикладную ошибку (нарушение ограничения, отказ в доступе). | 1. Успех: Сообщение об ошибке не содержит трассировки, путей файловой системы, имен внутренних узлов и иной служебной информации.<br><br>2. Успех: Возвращается обобщенный код/текст ошибки без конфиденциальных сведений. |
| Должна обеспечиваться минимизация состава информации, содержащейся в аутентификаторах доступа к API, путем исключения данных, раскрывающих структуру информационной системы или иные конфиденциальные сведения. | 1. Получить аутентификатор доступа к API example.ru (токен, ключ) для внутреннего и внешнего клиента.<br><br>2. Просмотреть состав данных аутентификатора (открытая часть токена, заголовки). | 1. Успех: Аутентификатор выдан и принимается API.<br><br>2. Успех: Аутентификатор не содержит сведений о структуре СПО и иных конфиденциальных данных. |
| При сетевом информационном взаимодействии внешних субъектов доступа с API через сеть «Интернет» должна обеспечиваться с учетом мер защиты информации ЗКС.1 – ЗКС.5. | 1. Выполнить `curl -sI http://example.ru/api/` и `openssl s_client -connect example.ru:443 -brief`.<br><br>2. Вызвать API внешнего субъекта по открытому HTTP и с недействительным сертификатом.<br><br>3. Проверить отключение небезопасных версий протоколов на интерфейсе API, доступном из сети «Интернет». | 1. Успех: HTTP отсутствует либо перенаправляется на HTTPS; TLS-рукопожатие завершается успешно.<br><br>2. Успех: Соединение отклонено.<br><br>3. Успех: Небезопасные версии протоколов отключены. |
| Субъект: Операторы СПО.<br><br>Условия: У Системы К2, К1.<br><br>Должен осуществляться ежегодный пересмотр режимов и настроек программного обеспечения, реализующего API, с целью выявления уязвимостей его конфигурации. | Проверить в эксплуатационной документации СПО сведения о ежегодном пересмотре режимов и настроек программного обеспечения, реализующего API example.ru, и о результатах выявления уязвимостей конфигурации. | Успех: Пересмотр проведен в пределах года; результаты зафиксированы. |
| Автопроверка Linux-хоста | `./check_all.sh --measure ЗПИ.1 --class K3`<br><br>`./check_all.sh --measure ЗПИ.1 --class K2 --with-enhancements` | Зафиксированы вердикты PASS/FAIL/SKIP/NA по локальным признакам (API-шлюз/reverse proxy, TLS, журналы). SKIP не считается провалом испытания СПО. |

Требования к усилению:

1) должен осуществляться ежегодный пересмотр режимов и настроек программного обеспечения, реализующего API, с целью выявления уязвимостей его конфигурации.
