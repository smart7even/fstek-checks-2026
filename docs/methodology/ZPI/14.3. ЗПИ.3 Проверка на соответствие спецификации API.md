# 14.3. ЗПИ.3 Проверка на соответствие спецификации API

**Скрипт:** `fstek_audit/checks/ZPI/ZPI_03.sh`

Цель: Обеспечение контроля запросов к интерфейсам взаимодействия приложений с целью выявления и блокирования запросов, не соответствующих утвержденной спецификации API.

Регламентирование: Не предъявляется.

Описание реализации, действий и результатов при испытаниях:

| Требование | Действие | Результат |
|------------|----------|-----------|
| При организации сетевого информационного взаимодействия между субъектами доступа (пользователями и приложениями) и объектами доступа в СПО посредством API в СПО должна быть определена спецификация API. | Открыть утвержденную спецификацию API СПО (OpenAPI или эквивалент) для https://example.ru/api и сопоставить ее с перечнем методов, доступных внутренним и внешним клиентам. | Успех: Спецификация определена, утверждена и описывает формат, структуру и ограничения запросов. |
| В СПО должна быть обеспечена возможность автоматической проверки запросов на предмет соответствия формату, структуре и ограничениям, предусмотренным разработанной спецификацией API. В СПО должно быть определено множество правил, описывающих виды запросов, не соответствующих спецификации API, подлежащие автоматическому блокированию средствами защиты информации до момента оказания запросом воздействия на приложение, доступное посредством API. | 1. Отправить на https://example.ru/api запрос, соответствующий спецификации.<br><br>2. Отправить запросы с полями вне схемы, неверным типом, нарушением ограничения и недопустимой структурой.<br><br>3. Убедиться, что блокирование выполнено средством защиты информации до воздействия на приложение. | 1. Успех: Запрос принят.<br><br>2. Успех: Запросы автоматически отклонены как не соответствующие спецификации.<br><br>3. Успех: Прикладная логика не обработала несоответствующий запрос; правило блокирования определено. |
| В СПО должен быть осуществлен пересмотр перечня и спецификации API на предмет выявления недокументированных, устаревших и неиспользуемых API и ресурсов, доступных внешним пользователям СПО посредством данных API, ежегодно или при изменении API. | 1. Сопоставить утвержденную спецификацию с фактически доступными внешним пользователям методами и ресурсами https://example.ru/api.<br><br>2. Проверить в документации дату последнего перечня/пересмотра спецификации и факт пересмотра при изменении API. | 1. Успех: Недокументированные, устаревшие и неиспользуемые API и ресурсы внешним пользователям недоступны.<br><br>2. Успех: Пересмотр выполнен ежегодно либо при изменении API. |
| В СПО должна осуществляться проверка поступающих к API запросов на соответствие формату, структуре и ограничениям, и блокировка запросов, не соответствующих спецификации API. | 1. Вызвать https://example.ru/api методом, не описанным в спецификации.<br><br>2. Вызвать описанный метод с телом, не соответствующим формату и структуре.<br><br>3. Вызвать описанный метод с параметром вне установленного ограничения. | 1. Успех: Запрос заблокирован (400/404/405).<br><br>2. Успех: Запрос заблокирован.<br><br>3. Успех: Запрос заблокирован. |
| Условия: У Системы К1.<br><br>В СПО должен быть осуществлен пересмотр перечня и спецификации API при изменении кода или конфигурации приложений, реализующих данные API. | Внести контрольное изменение кода или конфигурации приложения, реализующего API example.ru, и проверить, что перечень и спецификация API пересмотрены в том же цикле изменения. | Успех: Пересмотр перечня и спецификации выполнен при изменении кода или конфигурации. |
| Автопроверка Linux-хоста | `./check_all.sh --measure ЗПИ.3 --class K3`<br><br>`./check_all.sh --measure ЗПИ.3 --class K1 --with-enhancements` | Зафиксированы вердикты PASS/FAIL/SKIP/NA по локальным признакам (спецификация OpenAPI, проверка схемы, WAF). SKIP не считается провалом испытания СПО. |

Требования к усилению:

1) в СПО должен быть осуществлен пересмотр перечня и спецификации API при изменении кода или конфигурации приложений, реализующих данные API.
2) должен обеспечиваться автоматический анализ трафика сетевого информационного взаимодействия между внешними субъектами доступа и внешними API информационной системы на предмет выявления недокументированных, устаревших и неиспользуемых API и ресурсов, доступных внешним пользователям информационной системы посредством данных API.
