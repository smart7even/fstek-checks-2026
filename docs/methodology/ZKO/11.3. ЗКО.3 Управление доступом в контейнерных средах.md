# 11.3. ЗКО.3 Управление доступом в контейнерных средах

**Скрипт:** `fstek_audit/checks/ZKO/ZKO_03.sh`

Цель: Исключение несанкционированного доступа к объектам защиты в контейнерных средах.

Регламентирование: В эксплуатационной документации на информационную систему должны быть определены модели управления доступом в контейнерных средах, применяемых в информационной системе.

Описание реализации, действий и результатов при испытаниях:

| Требование | Действие | Результат |
|------------|----------|-----------|
| Субъект: Пользователи средства контейнеризации (непривилегированный пользователь, администратор средств контейнеризации, администратор безопасности).<br><br>При применении контейнерных сред должно обеспечиваться в соответствии с УПД.1 – УПД.4 управление доступом пользователей средства контейнеризации к контейнерам и их образам. | 1. Войти как администратор средств контейнеризации и выполнить `docker ps`, `podman ps`, `crictl ps`, `kubectl get pods -A`.<br><br>2. Войти как непривилегированный пользователь (не в группе `docker`/`podman`, RoleBinding только на свой namespace) и повторить те же команды, а также `docker run`, `kubectl run`.<br><br>3. Обратиться к `/var/run/docker.sock` / `/run/crio/crio.sock` от имени непривилегированного пользователя. | 1. Успех: Администратору доступны контейнеры и образы в пределах назначенной роли.<br><br>2. Успех: Непривилегированному пользователю операции отклонены либо ограничены своим namespace/проектом.<br><br>3. Успех: Прямой доступ к сокету средства контейнеризации запрещён (права 660, владелец root:docker/podman). |
| Субъект: Иные субъекты доступа (учётная запись рабочей нагрузки, сервисный токен Kubernetes, процесс на хосте).<br><br>Должно обеспечиваться управление доступом иных субъектов доступа к контейнерам и их образам. | 1. Из контейнера A выполнить `docker.sock` mount-сценарий: `kubectl apply` манифеста с volume `/var/run/docker.sock` и `crictl ps` внутри пода.<br><br>2. Использовать default ServiceAccount для `kubectl get secrets` / pull чужого образа из внутреннего реестра.<br><br>3. С хоста от имени системного пользователя без роли выполнить `podman images`. | 1. Успех: Монтирование сокета и управление чужими контейнерами отклонены политикой (PSS/Kyverno/admission).<br><br>2. Успех: Сервисному токену недоступны чужие образы и секреты pull.<br><br>3. Успех: Доступ к образам без назначенных прав отклонён. |
| В соответствии с УПД.2 должно обеспечиваться разграничение прав: запрет избыточных привилегий при запуске контейнеров и доступе к объектам хоста. | 1. Непривилегированным пользователем выполнить `docker run --privileged`, `podman run --privileged`, `kubectl apply` с `privileged: true` и `hostPID: true`.<br><br>2. Попытаться смонтировать `/`, `/etc`, `/var` хоста в контейнер (`-v /:/host`, `hostPath`).<br><br>3. Проверить RBAC: `kubectl auth can-i create pods --as=<user>` и членство в группе `docker`. | 1. Успех: Запуск привилегированного контейнера отклонён.<br><br>2. Успех: Монтирование чувствительных путей хоста заблокировано.<br><br>3. Успех: Права соответствуют модели доступа; избыточные роли отсутствуют. |
| В соответствии с УПД.3 – УПД.4 должны вестись учётные записи субъектов контейнерной среды, пересматриваться права и регистрироваться неуспешные попытки доступа. | 1. Создать и отозвать учётную запись оператора: `kubectl create sa`, RoleBinding; удалить из группы `docker`.<br><br>2. Выполнить неуспешный `docker login` и `kubectl` без токена.<br><br>3. Сверить журнал доступа (auditd, Kubernetes audit, journalctl). | 1. Успех: Жизненный цикл учётной записи отработан; после отзыва доступ прекращён.<br><br>2. Успех: Неуспешные попытки зарегистрированы.<br><br>3. Успех: Записи соответствуют РСБ и модели доступа из эксплуатационной документации. |
| Автопроверка Linux-хоста | `./check_all.sh --measure ЗКО.3 --class K3` | Зафиксированы вердикты PASS/FAIL/SKIP/NA по локальным признакам (права сокета docker/podman, группа доступа, отсутствие `--privileged`, RBAC/admission). SKIP не считается провалом испытания СПО. |
