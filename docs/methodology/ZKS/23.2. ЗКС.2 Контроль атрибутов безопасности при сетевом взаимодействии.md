# 23.2. ЗКС.2 Контроль атрибутов безопасности при сетевом взаимодействии

**Скрипт:** `fstek_audit/checks/ZKS/ZKS_02.sh`

Цель: Обеспечение доверенного сетевого взаимодействия на основе контроля уникальных признаков (атрибутов безопасности) субъектов доступа.

Регламентирование: Не предъявляются.

Описание реализации, действий и результатов при испытаниях:

| Требование | Действие | Результат |
|------------|----------|-----------|
| В информационной системе должен быть определен перечень атрибутов безопасности, в соответствии с которыми осуществляется контроль информации, получаемой и передаваемой за пределы контролируемой зоны. Атрибуты безопасности должны включать характеристики, позволяющие однозначно идентифицировать субъект доступа. | 1. В документации/политике МЭ открыть перечень атрибутов (сетевые адреса, порты, идентификаторы сертификатов, метки, зоны, FQDN субъектов).<br><br>2. Сверить, что атрибуты позволяют отличить субъектов: сравнить два субъекта с разными сертификатами/IP в правилах `nft list ruleset` / политике IPsec. | 1. Успех: Перечень атрибутов определен оператором и включает признаки субъекта доступа.<br><br>2. Успех: Атрибуты однозначно различают субъектов (нет общего any-any без идентификации). |
| Должно быть обеспечено формирование перечня атрибутов безопасности отправителей и получателей, включающих атрибуты сетевых соединений. | Выгрузить правила, содержащие атрибуты соединения: `nft list ruleset` (ip saddr/daddr, tcp sport/dport, ct state, iifname/oifname), `iptables -S`, политику IPsec (`ip xfrm policy`). Сопоставить с перечнем отправителей/получателей. | Успех: Перечень отправителей и получателей включает атрибуты сетевых соединений и отражен в правилах МЭ. |
| Должна быть обеспечена проверка соответствия атрибутов безопасности отправителя, получателя перед разрешением передачи данных. | 1. С легитимного субъекта (корректный клиентский сертификат/IP из allow-list) выполнить исходящую передачу: `curl --cert client.pem --key client.key https://<внешний получатель>` или `openssl s_client -connect <получатель>:443 -cert client.pem`.<br><br>2. Повторить с нарушенным атрибутом: просроченный/чужой сертификат, подмена source IP, неверный порт. | 1. Успех: При совпадении атрибутов передача разрешается.<br><br>2. Успех: При несовпадении атрибутов исходящая передача блокируется до отправки данных. |
| Должна быть обеспечена проверка соответствия атрибутов безопасности отправителя, получателя перед приемом данных. | 1. На входящем сервисе за КЗ принять соединение от субъекта с валидными атрибутами: `openssl s_client -connect <FQDN>:443 -cert good.pem` / mTLS nginx `ssl_verify_client`.<br><br>2. Повторить с self-signed/чужим сертификатом и с адреса вне allow-list: `openssl s_client -connect <FQDN>:443 -cert bad.pem`, `nc -zv <IP> 443` с чужого адреса. | 1. Успех: Прием разрешен только при соответствии атрибутов отправителя и получателя.<br><br>2. Успех: Соединение с неверными атрибутами отклоняется (handshake fail / nft drop) до обработки полезной нагрузки. |
| Должно быть обеспечено применение правил межсетевого экранирования на межсетевых экранах, учитывающих атрибуты безопасности с учетом меры защиты информации МСЭ.3. | 1. На МЭ найти правила с атрибутами субъектов: `nft list ruleset \| grep -E 'saddr\|daddr\|dport\|iifname'`, `iptables -S`.<br><br>2. Сгенерировать нарушение атрибута (чужой src, запрещенный dport) и проверить drop+log. | 1. Успех: Правила МЭ учитывают атрибуты безопасности, а не только «открытый порт».<br><br>2. Успех: Несоответствие атрибута блокируется в соответствии с МСЭ.3. |
| Операции с атрибутами должны регистрироваться с учетом мер защиты информации РСБ.1 – РСБ.5. | 1. Проверить журналирование МЭ: `nft list ruleset \| grep -i log`, `iptables -S \| grep LOG`.<br><br>2. Изменить/применить правило атрибута (на стенде) либо вызвать отказ в соединении и найти событие в `journalctl` / журнале РСБ (кто, когда, какой атрибут, результат). | 1. Успех: Операции проверки/изменения атрибутов и отказы регистрируются.<br><br>2. Успех: Запись содержит идентификатор субъекта, время и результат контроля. |
| Реализация указанных мер обеспечивается за счет применения межсетевых экранов и (или) многофункциональных межсетевых экранов. | `systemctl is-active nftables firewalld`; `nft list ruleset \| head`. | Успех: Контроль атрибутов выполняется на активном межсетевом экране (или МФМЭ). |
| Автопроверка Linux-хоста | `./check_all.sh --measure ЗКС.2 --class K3` | Зафиксированы вердикты PASS/FAIL/SKIP/NA по локальным признакам (активный МЭ, регистрация в правилах). Перечень атрибутов субъектов задается оператором и проверяется по правилам/документации (SKIP этого пункта не считается провалом испытания СПО). |
