# 22.5. ЗОО.5 Ограничение нагрузки

**Скрипт:** `fstek_audit/checks/ZOO/ZOO_05.sh`

Цель: Ограничение возможности создания условий для исчерпания ресурсов информационной системы.

Регламентирование: Не предъявляются.

Описание реализации, действий и результатов при испытаниях:

| Требование | Действие | Результат |
|------------|----------|-----------|
| Необходимо установить ограничение по максимальному числу одновременно установленных TCP-соединений с одного IP-адреса (максимальное число соединений определяется по методике и исходным данным оператора для различных типов прикладных сервисов, типов пользователей и (или) API-клиентов). | 1. Взять порог N из методики/профиля оператора (не задавать произвольное число). Проверить реализацию: `nft list ruleset \| grep -i limit`, `iptables -S \| grep -iE 'connlimit\|hashlimit'`, `nginx limit_conn`, HAProxy `maxconn`/`stick-table`.<br><br>2. С одного IP открыть N+1 параллельных TCP-сессий на сервис (`seq \| xargs -P ... nc` или `ab`/`wrk` с числом соединений > N) и N сессий с другого IP. | 1. Успех: Ограничение connlimit/limit_conn задано значением из методики оператора.<br><br>2. Успех: Соединения сверх N с одного IP сбрасываются/отклоняются; в пределах N и с другого IP сервис отвечает. |
| Необходимо установить ограничение по скорости ответа от системы доменных имен (DNS-сервера). | 1. В конфигурации DNS найти rate-limit: BIND `rate-limit { responses-per-second ... }`, Unbound `ratelimit`, Knot/PowerDNS эквивалент (значение — из методики оператора).<br><br>2. С тестового адреса выполнить поток `dig @<DNS> <имя> +time=1` с частотой выше операторского лимита и параллельно одиночный `dig` с другого адреса. | 1. Успех: На DNS-сервере включено ограничение скорости ответов с параметром оператора.<br><br>2. Успех: Избыточные ответы ограничиваются (dropped/slipped); легитимный одиночный запрос получает ответ. |
| Необходимо установить ограничение по максимальному числу одновременно выполняемых запросов в секунду на прикладном уровне с одного IP-адреса (максимальное число запросов определяется по методике и исходным данным оператора для запросов, поступающих от веб-интерфейсов, мобильных приложений, API-интерфейсов, интерфейсов администрирования). | 1. Сверить RPS-лимит оператора с `limit_req` nginx, `mod_evasive`, HAProxy `http-request deny`/`stick-table http_req_rate`, nft `limit rate`.<br><br>2. С одного IP превысить лимит: `wrk -t1 -c1 -d10s --latency https://<FQDN>/` или `ab -n ... -c ...` с RPS > порога; с другого IP выполнить одиночный `curl -I https://<FQDN>/`. | 1. Успех: Прикладной лимит запросов/с задан по методике оператора для заявленных типов интерфейсов.<br><br>2. Успех: Избыточные запросы получают 429/reject/drop; одиночный запрос с другого IP успешен. |
| При реализации меры по ограничению скорости в информационной системе необходимо обеспечить мониторинг трафика в информационной системе и выявление аномального поведения. | 1. Проверить сбор метрик трафика и алертов (node_exporter/netdata/Zabbix, журналы МЭ `nft log`, SIEM).<br><br>2. Во время превышения лимита открыть график pps/RPS и журнал: факт аномалии (spike, limit hit) должен появиться без подбора «типового» порога Linux. | 1. Успех: Мониторинг трафика включен.<br><br>2. Успех: Аномальное превышение лимита оператора зафиксировано (метрика/журнал/алерт). |
| Автопроверка Linux-хоста | `./check_all.sh --measure ЗОО.5 --class K3` | Зафиксированы вердикты PASS/FAIL/SKIP/NA по локальным признакам (rate-limit/connlimit, DNS RRL, стек мониторинга). Пороги соединений и RPS не выводятся скриптом — только наличие механизмов; числовые значения задает оператор. SKIP не считается провалом испытания СПО. |
