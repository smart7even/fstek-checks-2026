# 13.1. ЗВТ.1 Защита пользовательских данных

**Скрипт:** `fstek_audit/checks/ZVT/ZVT_01.sh`

Цель: Обеспечение защиты пользовательских данных, передаваемых, обрабатываемых и хранящихся в составе веб-приложения.

Регламентирование: В эксплуатационной документации для СПО должны быть определены:

- объекты доступа, содержащиеся в веб-приложении;
- перечень типов пользователей веб-приложения.

Описание реализации, действий и результатов при испытаниях:

| Требование | Действие | Результат |
|------------|----------|-----------|
| Субъект: Пользователи и приложения СПО.<br><br>Сетевое информационное взаимодействие между субъектами доступа и объектами доступа (пользователями и приложениями) должно осуществляться посредством программного интерфейса приложений, защита данных в котором обеспечивается в соответствии с мерой защиты информации ЗПИ.1. | 1. Открыть в веб-браузере https://example.ru/admin и https://example.ru/public, выполнить типичные операции чтения и изменения пользовательских данных.<br><br>2. Выполнить `curl -sI http://example.ru/api/` и `curl -sI https://example.ru/api/`.<br><br>3. Успех: Операции выполняются только через программный интерфейс СПО; прямого доступа к хранилищу пользовательских данных нет.<br><br>2. Успех: HTTP-доступ к API отсутствует либо перенаправляется на HTTPS.<br><br>3. Успех: Состав и защита данных API соответствуют мере ЗПИ.1. |
| Субъект: Внутренние непривилегированные пользователи (1), внутренние привилегированные пользователи (2), внешние пользователи (3).<br><br>Доступ субъектов доступа к пользовательским данным, хранящимся в веб-приложении, а также доступ к функциям веб-приложения должен осуществляться в соответствии с мерой защиты информации УПД.2. | 1. Войти в СПО на example.ru/admin с правами непривилегированного пользователя и обратиться к чужим пользовательским данным и к функции, не входящей в роль.<br><br>2. Войти в СПО на example.ru/public с правами внешнего пользователя и обратиться к внутренней функции example.ru/admin. | 1. Успех: Доступ к чужим данным и к функции вне роли отклонен.<br><br>2. Успех: Разрешенная операция выполнена; доступ соответствует наименьшим привилегиям.<br><br>3. Успех: Доступ к внутренней функции отклонен. |
| Сетевое взаимодействие между субъектами и объектами доступа (пользователями и приложениями) должно осуществляться с учетом мер защиты информации ЗКС.1 – ЗКС.5. | 1. Выполнить `curl -I http://example.ru/admin` и `openssl s_client -connect example.ru:443 -brief`.<br><br>2. Передать пользовательские данные по открытому HTTP на example.ru/admin. | 1. Успех: HTTP перенаправляется на HTTPS либо отклоняется; TLS-рукопожатие завершается успешно.<br><br>2. Успех: TLS 1.0/1.1 и иные небезопасные протоколы отключены.<br><br>3. Успех: Передача пользовательских данных по открытому каналу не принята. |
| Автопроверка Linux-хоста | `./check_all.sh --measure ЗВТ.1 --class K3` | Зафиксированы вердикты PASS/FAIL/SKIP/NA по локальным признакам (веб-стек, TLS, аутентификация/ACL, межсетевой экран). SKIP не считается провалом испытания СПО. |

Требования к усилению:

1) в СПО должно быть исключено кэширование пользовательских данных, определяемых оператором, в веб-браузере (например, путем использования соответствующих директив заголовков Cache-Control, Pragma протокола передачи гипертекста).
2) в СПО должны быть отключены функции автоматического заполнения форм (например, путем установления соответствующего значения атрибута Autocomplete протокола передачи гипертекста) для полей, предназначенных для ввода пользовательских данных, определяемых оператором.
3) в СПО должна обеспечиваться защита пользовательских данных от компрометации посредством межсайтового скриптинга путем настройки соответствующих заголовков безопасности протокола передачи гипертекста.
4) в СПО должна обеспечиваться защита пользовательских данных от компрометации посредством подмены (перекрытия) элементов графического интерфейса путем контроля вложенности контекстов отображения.
