# Contributing

## Ветки и scope работы

Имя ветки должно отражать **текущую** задачу, а не уже закрытую или смешанную
работу из прошлого.

Формат для agent-driven изменений:

```text
agent/fstek-<краткий-slug-задачи>
```

Примеры: `agent/fstek-fleet-orchestrator`, `agent/fstek-audit-engine-refactor`.

### Когда создавать новую ветку

Создавай **новую** ветку от актуального `main`, если выполняется хотя бы одно
условие:

- начинается **новая самостоятельная задача** (новая фича, новый этап roadmap,
  отдельный bugfix), а не продолжение текущего PR;
- предыдущая ветка уже **смержена** или её scope больше не совпадает с тем, что
  делаешь сейчас;
- в открытом PR накопились изменения из **разных несвязанных тем** — лучше
  довести текущий PR и вынести следующую тему в отдельную ветку;
- имя ветки перестало описывать работу (признак, что пора новая ветка).

### Когда оставаться в текущей ветке

- правки по review того же PR;
- доработки и тесты **той же** фичи до merge;
- мелкие fixup-коммиты в рамках одного scope.

### Практика для агентов (Codex / Cursor)

Перед началом работы сверь scope с именем ветки. Если задача явно другая —
сначала `git fetch origin main && git checkout -b agent/fstek-<новый-slug> origin/main`,
а не продолжай нерелевантную ветку «за инерцией».

После merge PR следующая фича — **всегда** новая ветка от `main`.

## Стиль скриптов

- Одна мера — один файл в `fstek_audit/checks/<GROUP>/<CODE>.sh`.
- Общий запускатель: `check_all.sh`.
- Одиночная мера: `check_all.sh --measure <CODE>`.
- Режим усилений: `--with-enhancements` или `-e`.
- Скрипты не должны изменять систему: только чтение файлов, состояния служб, журналов и параметров ОС.
- Вывод параметров должен использовать статусы `PASS`, `FAIL`, `SKIP`.

## Проверка перед коммитом

```bash
bash tests/syntax.sh
```

Для содержательной проверки запускайте скрипты на целевых ОС с правами root или достаточными правами чтения системной конфигурации.
