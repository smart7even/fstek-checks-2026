# 23.3. ЗКС.3 Контроль доступа к внешним ресурсам

**Скрипт:** `fstek_audit/checks/ZKS/ZKS_03.sh`

Цель: Исключение несанкционированного доступа внутренних пользователей к внешним информационным ресурсам (системам).

Регламентирование: В эксплуатационной документации на систему защиты информации должен быть определен:

- порядок ведения списка разрешенных и (или) запрещенных ресурсов.

Описание реализации, действий и результатов при испытаниях:

| Требование | Действие | Результат |
|------------|----------|-----------|
| Должен быть сформирован и поддерживаться в актуальном состоянии список внешних ресурсов, необходимых для выполнения функциональных задач (список разрешенных и (или) запрещенных ресурсов). | 1. Открыть список allow/deny в документации и в конфигурации прокси/МЭ: `/etc/squid/squid.conf` (`acl`, `http_access`), категории squidGuard, nft set внешних daddr, DNS RPZ.<br><br>2. Сверить дату актуализации списка с регламентом ведения. | 1. Успех: Список разрешенных и (или) запрещенных внешних ресурсов существует в СЗИ.<br><br>2. Успех: Порядок ведения соблюдается, список актуален. |
| Должен быть реализован контроль доступа пользователей, приложений и сетевых сервисов информационной системы к ресурсам внешних сетей, включая сеть «Интернет», в соответствии со списком разрешенных и (или) запрещенных ресурсов. | 1. С внутреннего АРМ через прокси: `curl -I --proxy http://<прокси>:3128 https://<разрешенный ресурс>`.<br><br>2. С того же АРМ: `curl -I --proxy http://<прокси>:3128 https://<запрещенный ресурс>`.<br><br>3. С сервисной УЗ приложения повторить исходящий запрос к внешнему API из списка и вне списка (`curl` без интерактивного браузера). | 1. Успех: Доступ к разрешенному ресурсу предоставляется.<br><br>2. Успех: Доступ к запрещенному ресурсу отклоняется прокси/МЭ.<br><br>3. Успех: Контроль применяется и к приложениям/сетевым сервисам, не только к пользователям. |
| Должны быть заблокированы попытки доступа к неразрешенным ресурсам внешних сетей, включая сеть «Интернет». | 1. `curl -vk --proxy http://<прокси>:3128 http://<запрещенный URL>` и прямой обход прокси `curl --noproxy '*' https://<запрещенный URL>`.<br><br>2. DNS-запрос к запрещенному имени: `dig @<внутренний DNS> <запрещенный домен>`.<br><br>3. Проверить журнал: `grep <URL> /var/log/squid/access.log` или `journalctl` / nft log. | 1. Успех: Запрос через прокси блокируется; прямой исходящий HTTPS/HTTP без прокси также блокируется правилом OUTPUT (nft/iptables reject/drop).<br><br>2. Успех: Разрешение запрещенного имени не приводит к доступу (NXDOMAIN/sinkhole или последующий drop).<br><br>3. Успех: Попытка зафиксирована (пользователь/сервис, URL или daddr). |
| Должен быть определен список разрешенных в информационной системе используемых сетевых протоколов, сетевых приложений и сервисов. | 1. Сверить перечень протоколов/сервисов в документации с ACL: разрешенные `tcp dport {80,443,...}` в `nft list ruleset` / OUTPUT iptables; запрет прочих.<br><br>2. С внутреннего хоста: `nc -zv 1.1.1.1 443` (если HTTPS разрешен) и `nc -zv 1.1.1.1 23` / `nc -zv 1.1.1.1 445`. | 1. Успех: Разрешенные протоколы, приложения и сервисы определены и отражены в правилах.<br><br>2. Успех: Разрешенный протокол проходит; неразрешенные порты/службы блокируются. |
| Автопроверка Linux-хоста | `./check_all.sh --measure ЗКС.3 --class K3` | Зафиксированы вердикты PASS/FAIL/SKIP/NA по локальным признакам (контроль исходящего доступа: squid/nft OUTPUT, журналирование). SKIP не считается провалом испытания СПО. |

Требования к усилению:

1) должен проводиться морфологический анализ запрашиваемых веб-ресурсов перед их открытием;
2) должна использоваться категоризация веб-ресурсов.
