# 11.2. ЗКО.2 Регистрация событий безопасности в контейнерных средах

**Скрипт:** `fstek_audit/checks/ZKO/ZKO_02.sh`

Цель: Определение состава и содержания информации о событиях безопасности, подлежащих регистрации в контейнерных средах.

Регламентирование: В эксплуатационной документации на информационную систему должны быть определены требования к регистрации событий безопасности при применении контейнерных сред.

Описание реализации, действий и результатов при испытаниях:

| Требование | Действие | Результат |
|------------|----------|-----------|
| При применении контейнерных сред должна обеспечиваться в соответствии с РСБ.1 – РСБ.5 регистрация попыток осуществления несанкционированного доступа к средству контейнеризации. | 1. С хоста без членства в группе `docker`/`podman` выполнить `docker ps`, `podman ps`, `crictl ps` и обращение к `/var/run/docker.sock` / `/run/podman/podman.sock` / `/run/crio/crio.sock`.<br><br>2. Выполнить `kubectl get pods` без действительного kubeconfig/токена.<br><br>3. Открыть журнал (`journalctl -u docker -u crio`, auditd по сокету, журнал API Kubernetes). | 1. Успех: Доступ к средству контейнеризации отклонён.<br><br>2. Успех: Запрос к API оркестратора отклонён.<br><br>3. Успех: Попытка НСД зарегистрирована с идентификатором субъекта, временем и объектом доступа. |
| Должна обеспечиваться регистрация попыток аутентификации пользователей средств контейнеризации. | 1. Выполнить успешный вход: `docker login <реестр>`, `podman login`, `crictl pull` с учётными данными, `kubectl auth can-i list pods` от имени администратора средств контейнеризации.<br><br>2. Повторить вход с неверным паролем/токеном.<br><br>3. Проверить журнал аутентификации реестра, cri-o и API Kubernetes. | 1. Успех: Успешная аутентификация зарегистрирована.<br><br>2. Успех: Неуспешная попытка зарегистрирована.<br><br>3. Успех: В записи указаны субъект, результат и время. |
| Должна обеспечиваться регистрация создания, модификации и удаления образов контейнеров. | 1. `docker pull` / `podman pull` / `crictl pull` тестового образа; `docker tag`; `docker rmi` / `podman rmi` / `crictl rmi`.<br><br>2. В Kubernetes: `kubectl set image deploy/<имя> <контейнер>=<новый-образ>` и откат.<br><br>3. Проверить журнал жизненного цикла образов. | 1. Успех: Создание, изменение тега и удаление образа зарегистрированы.<br><br>2. Успех: Смена образа в рабочей нагрузке зарегистрирована.<br><br>3. Успех: В записях указаны имя/digest образа и субъект. |
| Должна обеспечиваться регистрация получения доступа к образам контейнеров. | 1. Выполнить `docker save`, `podman save`, `crictl inspecti`, выгрузку из внутреннего реестра.<br><br>2. Выполнить `kubectl get secret` с данными pull и `docker pull` от имени непривилегированного пользователя.<br><br>3. Проверить журнал доступа к реестру и слоям образа. | 1. Успех: Чтение/выгрузка образа зарегистрированы.<br><br>2. Успех: Отказ непривилегированному субъекту зарегистрирован.<br><br>3. Успех: В записи указан идентификатор образа. |
| Должна обеспечиваться регистрация запуска и остановки средства контейнеризации с указанием причины остановки. | 1. `systemctl stop docker` / `systemctl stop crio` / остановка `podman.socket`; затем `systemctl start`.<br><br>2. Инициировать остановку по причине ошибки конфигурации (некорректный `daemon.json` / `crio.conf`) и восстановить.<br><br>3. Проверить `journalctl -u docker -u crio -u podman`. | 1. Успех: Запуск и штатная остановка зарегистрированы.<br><br>2. Успех: Остановка по причине ошибки зарегистрирована с указанием причины.<br><br>3. Успех: Причина остановки присутствует в журнале. |
| Должна обеспечиваться регистрация запуска и остановки контейнеров с указанием причины остановки. | 1. `docker run --name zko2 /bin/sleep 60`; `docker stop zko2`; `podman run` / `crictl runp` и `crictl stopp`.<br><br>2. Завершить контейнер изнутри (`kill 1`) и удалить: `docker rm`, `kubectl delete pod`.<br><br>3. Проверить `docker events`, `kubectl describe pod`, журнал cri-o. | 1. Успех: Запуск и остановка зарегистрированы.<br><br>2. Успех: Причина остановки (stop/kill/OOM/удаление) указана.<br><br>3. Успех: В записи есть идентификатор контейнера. |
| Должна обеспечиваться регистрация изменения назначения ролей. | 1. В Kubernetes: `kubectl create rolebinding` / `kubectl edit clusterrolebinding` — назначить и отозвать роль разработчика образов.<br><br>2. На хосте: добавить и исключить пользователя из группы `docker`/`podman` (`usermod -aG` / `gpasswd -d`).<br><br>3. Проверить auditd и журнал API Kubernetes (RBAC). | 1. Успех: Назначение и отзыв роли зарегистрированы.<br><br>2. Успех: Изменение членства в группе зарегистрировано.<br><br>3. Успех: В записи указаны субъект, роль и время. |
| Должна обеспечиваться регистрация модификации запускаемых контейнеров. | 1. `docker update --memory 64m <cid>`; `kubectl patch deploy/<имя> -p '{"spec":{"template":{"spec":{"containers":[{"name":"<c>","resources":{"limits":{"memory":"64Mi"}}}]}}}}'`.<br><br>2. `docker commit`, изменение mounts/capabilities: `podman update`, `kubectl exec` с записью в файловую систему при ненулевом `docker diff`.<br><br>3. Проверить журнал модификации рабочей нагрузки. | 1. Успех: Изменение ресурсов зарегистрировано.<br><br>2. Успех: Изменение образа/монтирований/файловой системы зарегистрировано.<br><br>3. Успех: Указан идентификатор контейнера и субъект. |
| Должна обеспечиваться регистрация выявления известных уязвимостей в образах контейнеров и некорректности их конфигурации. | 1. Просканировать образ: `trivy image <образ>`, `grype <образ>`.<br><br>2. Применить заведомо небезопасный манифест (`privileged: true`, хостовой PID) через `kubectl apply --dry-run=server` или admission.<br><br>3. Проверить отчёт сканера и журнал политики (Kyverno/Gatekeeper/Falco). | 1. Успех: Выявленные уязвимости зарегистрированы.<br><br>2. Успех: Некорректная конфигурация выявлена и зарегистрирована.<br><br>3. Успех: В записи указаны образ и перечень нарушений. |
| Должна обеспечиваться регистрация фактов нарушения целостности объектов контроля. | 1. Изменить файл в контейнере (`docker exec ... >> /bin/true`) и слой образа.<br><br>2. Запустить Falco/AIDE/`docker diff`.<br><br>3. Сверить журнал целостности с идентификатором контейнера/образа. | 1. Успех: Нарушение целостности внесено.<br><br>2. Успех: Контроль выполнен.<br><br>3. Успех: Факт нарушения целостности зарегистрирован. |
| Кроме того, должна обеспечиваться регистрация событий безопасности, относящихся к функционированию контейнера, с указанием идентификатора контейнера. Меры реализуются за счет встроенных механизмов средства контейнеризации и хостовой ОС. | 1. Сгенерировать события внутри контейнера: сетевое соединение, запись в файл, запуск процесса (`crictl exec`, `kubectl exec`).<br><br>2. Снять `docker logs`, `kubectl logs`, журнал Falco/auditd.<br><br>3. Сопоставить идентификатор контейнера (`docker inspect --format '{{.Id}}'`, `crictl ps -v`) с записями. | 1. Успех: События функционирования созданы.<br><br>2. Успех: События зарегистрированы.<br><br>3. Успех: В каждой записи указан идентификатор контейнера. |
| Автопроверка Linux-хоста | `./check_all.sh --measure ЗКО.2 --class K3` | Зафиксированы вердикты PASS/FAIL/SKIP/NA по локальным признакам (log-level docker/podman, journalctl lifecycle, auditd по сокету, события НСД/аутентификации). SKIP не считается провалом испытания СПО. |
